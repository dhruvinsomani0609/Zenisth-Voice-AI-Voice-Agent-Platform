Product Requirements Document (PRD): Voice Agent Scheduling Integration

1. Overview

Project: Zenisth Voice Agent
Feature: Dynamic AI Appointment Scheduling
Provider: Cal.com API v2
Goal: Enable the voice agent to autonomously check calendar availability, verify user details (name/email), and book meetings via real-time external API calls without human intervention.

2. Core Architecture

The scheduling feature was upgraded from a static, in-memory mock to a live, production-ready integration.

2.1 Service Layer Abstraction (app/services/calendar.py)

To maintain flexibility and avoid vendor lock-in, the integration uses an Abstract Base Class (ABC). * BaseCalendarService: Defines the strict async contract requiring get_available_slots and create_booking methods. * CalComService: The concrete implementation using the Cal.com v2 REST API. Uses httpx.AsyncClient for highly concurrent, non-blocking requests to avoid locking the Deepgram STT websocket loop.

2.2 LLM Tool Definitions (app/agent/functions.py)

The system registers two primary function-calling tools with Groq/Llama-3: 1. check_availability: Accepts a natural language date (e.g. "tomorrow", "next Monday") and returns formatted slots. 2. book_appointment: Accepts name, email, strict date, and time. Triggers the actual calendar invite email via the provider.

3. Technical Specifications & Problem Resolutions

During implementation, several platform-specific bugs and API nuances were resolved to ensure stability across operating systems.

3.1 Date Parsing without External Dependencies

  • Initial approach: Used the third-party dateparser library.
  • Problem: Environment inconsistency across virtual environments (.venv) caused fatal ModuleNotFoundError crashes during live calls.
  • Resolution: Replaced the library with a custom, highly robust Python Standard Library implementation (datetime & timedelta). It successfully parses "today", "tomorrow", "next Friday", "March 10", and standard ISO formats with zero external dependencies.

3.2 Timezone Resolution Framework

  • Problem: Timezone conversion (Asia/Kolkata) crashed on Windows environments because Windows does not ship with the IANA timezone database, causing zoneinfo.ZoneInfoNotFoundError.
  • Resolution: Added the tzdata (Time Zone Database) package directly to the project's requirements.txt and .venv.
  • Mechanism: Refactored all time formatters to use Python 3.9+ native zoneinfo module instead of pytz, ensuring forward-compatible and lightweight timezone resolution.

3.3 Cal.com API v2 Nuances

The implementation accurately handles Cal.com's strict REST API v2 requirements: * Slots Endpoint: Discovered that /v2/slots/available is deprecated. Successfully migrated to GET /v2/slots using start and end ISO 8601 boundary query parameters. * Bookings Endpoint: Discovered a header conflict. The /v2/bookings POST endpoint explicitly requires the older cal-api-version: 2024-08-13 header to authorize, while the slots endpoint requires 2024-09-04. A dynamic header injector _auth_headers(for_booking=True) was implemented to handle this transparently.

4. Conversational UX & Guardrails (app/agent/settings.py)

To prevent the agent from sending sensitive calendar invites to hallucinatory or misheard domains, a strict 4-Step Scheduling Protocol was injected directly into the LLM System Prompt:

The Protocol: 1. Check first: The agent is banned from confirming times before explicitly calling check_availability. It must only read out 2 to 3 slots to avoid overwhelming the user via audio. 2. Confirm slot: Wait for user selection. 3. Verify email spelling: Upon receiving an email address, the agent is forced to always read it back letter-by-letter (e.g. "d-h-r-u-v-i-n dot s-o-m-a-n-i at zenisth dot ai, is that correct?") before proceeding. 4. Error Recovery: If the booking API returns 409 (Slot Taken) or 422 (Invalid Data), the agent must gracefully apologize in plain English and prompt the user to re-spell the email or pick a new time.

The system is controlled via .env variables, preventing hardcoded secrets.
